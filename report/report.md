## 三、实验整体逻辑分析

### 2.1 本章节的逻辑主线

本章实验围绕 RISC-V 架构下的中断与异常处理机制 展开，主要解决操作系统如何响应突发事件，并在处理完成后恢复原程序执行的问题。

在正常运行过程中，CPU 按照程序指令依次执行任务。但是，当出现时钟中断、非法指令或断点异常等情况时，CPU 需要暂停当前程序，转而执行对应的处理程序。

为了保证原程序能够正常恢复，操作系统需要先保存被中断程序的执行状态，再根据 Trap 的类型进行相应处理，最后恢复之前保存的状态并返回原程序。

因此，本实验按照 “Trap 上下文保存与恢复 → Trap 入口与返回 → 中断与异常处理” 的主线展开。

其中，TrapFrame 负责保存程序的上下文，trapentry.S 负责底层的入口与返回，trap.c 则负责判断 Trap 类型并执行具体处理。三个部分相互配合，最终形成完整的 Trap 处理机制。

### 2.2 功能的逐步实现

1. **首先，理解 TrapFrame 并完善上下文恢复功能。**

当 CPU 发生 Trap 时，原程序的寄存器状态可能被后续处理程序修改。因此，在进入处理函数之前，需要先保存这些状态。

实验已经提供了 SAVE_ALL，用于将通用寄存器和部分控制状态寄存器保存到 TrapFrame 中。我们需要根据已有的保存方式，实现对应的 RESTORE_ALL，确保处理结束后能够正确恢复原程序的执行状态。

这一步是整个实验的基础，因为只有正确保存和恢复上下文，才能保证 Trap 处理不会破坏原程序。

2. **接着，实现 Trap 入口与 C 语言处理函数的连接。**

在完成上下文恢复功能后，需要完善 trapentry.S 中的 __alltraps。

该部分首先利用 SAVE_ALL 保存现场，然后将 TrapFrame 的地址作为参数传递给 trap()，使程序从汇编代码进入 C 语言编写的处理函数。

当 trap() 执行结束后，再通过 __trapret 和 RESTORE_ALL 恢复现场，最后执行 sret 返回原程序。

通过这一步，建立了完整的 Trap 进入和返回流程，为后续处理中断和异常提供了基础。

3. **然后，实现中断处理功能。**

在 trap.c 中，通过 trap_dispatch() 判断当前 Trap 属于中断还是异常，再调用对应的处理函数。

对于中断部分，主要实现 interrupt_handler()，其中重点是时钟中断。

当时钟中断发生时，程序调用 clock_set_next_event() 设置下一次时钟事件，并通过 ticks++ 记录中断次数。

当计数达到 TICK_NUM 的整数倍时，输出统计信息；累计输出达到 SHUTDOWN_AFTER 次后，调用关机接口结束运行。

通过时钟中断的连续触发，可以检验中断处理和上下文恢复机制是否正常工作。

4. **最后，实现异常处理功能。**

在 exception_handler() 中，根据 tf->cause 判断异常类型，主要完成非法指令异常和断点异常的处理。

处理过程中，除了输出对应的异常信息，还需要修改 tf->epc，使程序返回时能够跳过已经触发异常的指令，避免重复进入异常处理程序。

需要注意的是，不同异常指令的长度可能不同，因此要根据实际指令长度调整返回地址。

完成上述功能后，系统就能够正确区分中断和异常，执行对应处理，并在处理结束后恢复原来的执行状态。

### 功能模块二：中断与异常处理——异常处理部分

#### 模块功能描述

**需要实现/修改的函数：**

```c
void exception_handler(struct trapframe *tf);
```

**功能说明：**

本模块负责处理 CPU 执行过程中发生的异常，是整个 Trap 处理机制的一部分。

当异常发生时，系统首先通过 `trapentry.S` 保存上下文，再由 `trap_dispatch()` 将异常交给 `exception_handler()` 处理。

本模块主要完成以下功能：

1. **非法指令异常：** 识别 `CAUSE_ILLEGAL_INSTRUCTION`，输出异常地址，并根据实际指令长度修改 `tf->epc`，使程序跳过非法指令。
2. **断点异常：** 识别 `CAUSE_BREAKPOINT`，输出断点地址，区分 16 位和 32 位指令，正确调整返回位置。
3. **其他异常：** 调用 `print_trapframe(tf)` 输出现场信息，不额外修改程序状态。

处理结束后，函数返回统一的 Trap 返回流程，通过 `RESTORE_ALL` 恢复上下文，最后执行 `sret` 返回程序。

本模块的关键是**正确识别异常类型，并调整异常处理后的程序执行位置，避免重复触发同一异常。**

#### 最终提示词

以下是用于完成异常处理模块的最终提示词：

```markdown
[Prompt]

**任务**
- 完成异常处理模块 void exception_handler(struct trapframe *tf)，根据 Trap 原因正确分类和处理异常。

**操作要求**
- 直接修改并保存项目中的 kern/trap/trap.c。

**输出要求**
- 简要说明修改位置和验证结果，未运行的测试如实注明。

[RELY]

1. 宏定义：
- CAUSE_ILLEGAL_INSTRUCTION：非法指令异常。
- CAUSE_BREAKPOINT：断点异常。

2. 数据结构：
- 复用 struct trapframe，不修改布局。
- tf->cause：判断异常类型。
- tf->epc：读取和调整 Trap 返回位置。

3. 已有函数：
- print_trapframe(tf)：输出完整现场。
- cprintf() 等已有输出接口。
- 具体定义和输出格式以框架及测试要求为准。

4. 修改范围：
- 仅修改 exception_handler() 及必要的局部辅助定义。
- 不修改函数签名、已有分发逻辑、其他函数或内核模块。

[GUARANTEE]

- 实现 void exception_handler(struct trapframe *tf)。
- 正确处理非法指令、断点及其他异常，并与统一 Trap 返回流程衔接。
- 除规定的 tf->epc 调整外，保持其他现场不变。

[SPECIFICATION]

1. 非法指令异常：
- 按规定格式输出 “Illegal instruction at ...”，包含调整前的异常地址。
- 根据实际指令长度更新 tf->epc，跳过触发指令。

2. 断点异常：
- 按规定格式输出 “Breakpoint at ...”，包含调整前的断点地址。
- 区分 16 位压缩断点和 32 位普通断点，分别增加 2 或 4 字节。

3. 指令长度：
- 根据实际编码判断实验涉及的 16/32 位指令长度。
- 不按异常类型固定长度，不统一增加固定偏移。

4. 其他异常：
- 调用 print_trapframe(tf)，保持 tf->epc 不变，不额外实现恢复策略。

5. 返回位置与 PC：
- 设触发异常的指令地址为 A，指令长度为 L。
- 对本实验要求跳过的非法指令和断点异常，将 tf->epc 更新为 A + L；其他异常保持不变。
- 修改 tf->epc 不会立即改变 PC，处理函数仍正常执行并返回。
- 后续 RESTORE_ALL 将 tf->epc 写回 sepc，sret 再令 PC = sepc，使指定异常返回后执行下一条指令。
- 不直接修改硬件 sepc，不自行恢复上下文、执行 sret 或改变返回特权级。

6. 验收条件：
- 输出符合规定格式。
- 指定异常返回后继续执行下一条指令，不反复触发同一异常。
- 其他异常输出现场且不改变返回位置。
- 不破坏被打断执行流的寄存器与返回状态。
```

#### 实现迭代过程

本模块采用一次完整提示词进行实现。提示词重点明确了异常分类、指令长度判断、返回地址调整以及修改范围等要求。

##### 第一次迭代

**设计思路：**

首先，向 AI 提供 `exception_handler()` 的函数签名，以及 `tf->cause`、`tf->epc` 等已有接口，明确只需要实现异常处理，不修改其他 Trap 处理逻辑。

其次，在 `[SPECIFICATION]` 中分别规定非法指令异常、断点异常和其他异常的处理方式。

其中，重点强调不能直接将 `tf->epc` 固定增加 4，而需要根据指令编码判断长度。这是因为 RISC-V 同时支持 16 位压缩指令和 32 位普通指令，如果返回地址调整错误，可能导致程序执行位置异常。

最后，明确异常处理函数只负责更新 TrapFrame，不直接执行上下文恢复和 `sret`，避免破坏已有的 Trap 返回机制。

**本次提示词的关键设计：**

1. **通过 `[RELY]` 明确依赖关系：** 提供已有宏、数据结构和函数，要求 AI 复用框架接口。
2. **通过 `[GUARANTEE]` 限制实现范围：** 只修改异常处理相关代码，保持其他寄存器状态和处理逻辑不变。
3. **通过 `[SPECIFICATION]` 明确处理细节：** 区分不同异常，正确计算指令长度，并规定 `tf->epc` 的修改方式。
4. **明确返回流程：** 将异常处理与 `RESTORE_ALL`、`sret` 联系起来，避免 AI 在处理函数内部重复执行 Trap 返回操作。

**最终结果：**

通过本次提示词设计，异常处理模块的实现要求已经明确，包括异常类型判断、信息输出、指令长度识别和返回地址更新。


**关键改进点总结：**

1. 明确区分非法指令异常、断点异常和其他异常的处理方式，避免遗漏分支。
2. 在 `[SPECIFICATION]` 中强调根据实际指令长度调整 `tf->epc`，避免固定偏移导致返回地址错误。
3. 明确 `tf->epc`、`sepc` 和 `sret` 之间的关系，确保异常处理能够正确衔接统一的 Trap 返回流程。
4. 限定代码修改范围，避免 AI 修改其他已经实现的功能。

## 六、实验总结与收获

**1. 本实验知识点与 OS 原理知识点的联系和区别**

| 本实验知识点 | OS 中知识点 | 关系 | 差异 |
|---|---|---|---|
| Trap 上下文保存与恢复 | 上下文保存与恢复 | 二者都是为了保留程序执行现场，使程序能够在暂停后继续执行。 | 本实验主要处理一次中断或异常发生时的现场保存与恢复，通常返回原来的执行流；进程上下文切换则可能切换到另一个进程，还需要处理进程相关的其他状态。 |
| Trap 入口与返回 | 中断和异常处理机制 | 二者都依赖硬件提供的 Trap 机制，使 CPU 从正常执行流程进入内核处理流程，并在处理完成后返回。 | OS 原理主要介绍中断和异常处理的通用机制，本实验则结合 RISC-V 架构，具体实现了 Trap 入口设置、上下文保存、异常分发和现场恢复等过程。 |
| `stvec`、`scause` 与 `trap_dispatch()` | 中断与异常的响应和分发 | 中断由外部事件异步触发，异常由当前指令同步触发。实验通过 `stvec` 设置统一入口，保存 `scause` 后，由 `trap_dispatch()` 区分中断和异常，再交给相应的处理函数。 |
| `trapframe`、`SAVE_ALL` 与 `sret` | 现场保护与恢复 | 实验将寄存器和返回地址等信息保存到栈上的 `trapframe` 中，处理结束后恢复现场，通过 `sret` 返回。时钟中断保留 `tf->epc`，从原定位置继续执行。实验中的断点和非法指令处理则按指令长度更新 `tf->epc`，跳过触发异常的指令。 |
| 定时器中断与 `ticks` | 时钟管理 | 操作系统可利用时钟中断计时和驱动调度。实验在每次时钟中断中安排下一次时钟事件，并累计 `ticks`、定期输出统计信息，体现了周期性时钟管理的基本机制。 |
| `local_intr_save()` 与 `local_intr_restore()` | 临界区保护 | 分配器进入临界区前保存并关闭当前 hart 的中断，退出时恢复原有中断状态，以避免同一 hart 的中断处理打断分配器操作。多个 hart 访问同一份共享数据时，还需要跨核同步。 |

**2. OS 原理中重要但本实验没有对应上的知识点**

- **进程调度与切换**。例如时间片耗尽后选择下一个进程，保存当前进程的上下文并恢复下一个进程的上下文。
- **系统调用**。例如用户程序通过 `ecall` 请求内核服务，内核根据系统调用号分发请求、检查参数并返回结果。
- **缺页异常恢复**。例如根据缺页原因建立页表映射或调入页面，处理完成后重试触发缺页的指令。
- **设备中断的完整处理**。例如识别中断来源、确认中断，并由设备驱动处理相应的 I/O 事件。

### AI 协作开发的经验

- 本次开发中，先明确需要修改的代码位置和功能范围，再让 AI 阅读已有的
`SAVE_ALL`、`struct trapframe`
等定义后完成指定部分，避免对其他模块造成影响。
- 生成代码后，不能只看 AI
的说明，还需要使用项目工具链编译，并通过反汇编检查寄存器偏移和函数调用方式。对于汇编代码，结合
TrapFrame 的结构布局逐项核对，比单纯依赖 AI 判断更可靠。
